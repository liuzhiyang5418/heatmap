## 1. 三条独立证据

### 证据 A · main 分支 CI 从未失败

```
GET /actions/runs?branch=main&status=failure
→ {"total_count": 0, "workflow_runs": []}
```

`main` 上的 CI 从建仓至今 **0 次失败**。最近的 7 次运行（`#59`–`#65`）连续为 `success`。

### 证据 B · 历史失败全部发生在分支上，且是真实缺陷而非随机抖动

仓库共有 9 次失败运行，全部集中在两个分支的两个时间点：

| 运行 | 日期 | 分支 | 起因 |
|---|---|---|---|
| #44 / #45 | 2026-11-17 | `feat/nfr2-nfr3-completion` | 提交信息即 "fix: **stabilize** cross-platform NFR fixtures" —— 团队当时正在处理跨平台夹具不稳，失败两次后改用「双跑自一致」绕过（即 D-3 决策） |
| #12 / #13 | 2026-11-02 | `feat/sprint1-member1-member6` | Sprint 1 加 Dashboard / 英文化的过渡提交 |

这两组都是**特定变更引入的真实问题**（有明确的提交内容对应），不是同样的代码偶尔失败——不符合 flaky 的典型特征。

> 补充：`#44/#45` 的失败恰好印证了 WP-S3-2.3 的发现——当时没找到真因（Windows 上 `write_text` 写 CRLF），只能把断言弱化。Sprint 3 修掉根因后，同一份契约在两个平台都通过。

### 证据 C · 本地高风险用例重复执行

对最可能不稳定的三组用例各重复 3 次（同一台机器，连续执行）：

| 组 | 重复结果 |
|---|---|
| 性能用例（`-m slow`，伸缩性比值断言） | 3/3 通过（`...` × 3） |
| `symlink` / `clock` / `determinism` / `frozen` / `scanner_codes` | 3/3 通过，**skip 模式完全一致**（`ss...sss` × 3） |
| 常规全量（`-m "not slow"`）+ 覆盖率 | 通过，覆盖率恒为 92.79% |

skip 模式逐字符一致这一点值得单独说明：如果符号链接用例在不同运行间时而 skip 时而通过，就会出现 `s` 与 `.` 交替。三次完全一致说明**跳过判定是确定性的**（由平台能力决定，不由时序决定）。

## 2. 为什么这个项目不容易 flaky

排查过程中确认，几个主要的 flaky 来源在设计阶段就被消掉了：

| 常见 flaky 来源 | 本项目的处理 |
|---|---|
| **依赖当前时间** | 时钟可注入（`FixedClock`），且 `tests/test_clock.py` 会全仓检索 `datetime.now(` / `perf_counter` / `time.time`，出现即红灯 |
| **依赖机器速度** | 性能守卫用相对倍数（伸缩性 < 8×、灾难上界 60s），不写绝对秒数 |
| **依赖工作目录 / 路径** | 夹具全部在 `tmp_path` 下构建；指纹断言「路径无关」 |
| **依赖全局 git 配置** | 所有建仓用例显式传 `-c user.name/user.email`（Sprint 1 曾因此踩坑，见 `test_git.py` 的修复） |
| **符号链接权限** | Windows 上无法创建时 `pytest.skip`，而不是让用例随机失败 |
| **网络** | 测试不访问网络；GitPython 只读本地仓库 |
| **排序不稳定** | scanner / todo / ranking 都做了确定性排序，`canonical()` 还做了 sort_keys |

## 3. 如果未来出现 flaky，按这个顺序查

留作运维指引，不重复造轮子：

1. **先看 skip 模式有没有变**：`pytest -q` 的输出里 `s` 的位置变了，说明是环境判定问题（权限、平台能力），不是逻辑问题。
2. **性能用例失败先看比值而不是绝对时间**：日志里 `ratio` 是多少。若在 6–8 之间徘徊，说明机器负载波动（放宽到 10× 是合理的）；若是几十倍，那是真的退化。
3. **指纹用例失败先比对「哪个快照」**：`test_fingerprints_match_committed_baseline` 断言的是整个 dict，失败时 pytest 会打印实际值，直接与 `tests/fixtures/frozen_fingerprints.json` 对比，能立刻定位是哪一个快照、哪一类字段漂移。
4. **时间相关用例失败优先怀疑注入**：检查是否有人新增了直接用 `datetime.now()` 的代码（`test_time_sources_are_confined_to_clock_module` 会先报出来）。
5. **连续失败两次以上再动代码**：单次失败先 `rerun` 该 job；如果 rerun 就绿，说明是基础设施抖动（runner 资源），不要为它改断言。

## 4. 已知的残留风险（不在本次修复范围）

| 风险 | 说明 | 建议 |
|---|---|---|
| 符号链接用例在 Windows 上始终 skip | 不是失败，但覆盖面在该平台缺一块 | 报告里如实记为 skip，不声称已覆盖 |
| 浏览器用例只在 Linux/3.12 跑 | 需要 `HEATMAP_CHROME` | 同上 |
| 性能用例只在 Linux/3.11 跑 | 避免 6 个组合重复测量 | 若未来需要跨平台性能对比，另立 WP |
| 依赖 GitPython 版本的 `commit.stats` 行为 | 版本升级可能改变 churn 计算 | `pyproject.toml` 已限定 `GitPython>=3.1`，升级时需重跑冻结指纹 |

---

## 5. 结论

**当前没有证据表明测试套件 flaky。**

- `main` 分支 CI 失败次数：**0**
- 本地高风险用例重复 3 次：**全部一致**
- 历史 9 次失败：**全部可归因到具体变更**（Sprint 1 功能开发、M4 夹具稳定化过渡期），非随机抖动

因此 WP-S3-2.5 的处置是**「记录结论 + 留下排查指引」**，不做无依据的"加固"。若后续出现真实 flaky，按 §3 的顺序定位，并为该用例补一条最小复现。
