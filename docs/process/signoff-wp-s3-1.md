# 决策 1 · 12 类故障是否就是 NFR-2 的验收分母

### 背景

NFR-2.1 的指标是「12 类故障注入场景，崩溃率 0」。这个「12」来自 Sprint 2 的排期计划，
需要团队确认：**这就是我们对外承诺的分母**，还是需要增减。

### 现状证据

实现已覆盖以下 12 类，分布在 5 个测试文件共 39 个用例：

| # | 故障类 | 测试位置 |
|---|--------|----------|
| 1 | 非 ASCII 文件名 | `test_robustness.py::test_non_ascii_path_is_analyzed` |
| 2 | 二进制文件 | `test_robustness.py::test_file_content_boundaries_are_audited` |
| 3 | 超大文件（>2 MB） | 同上 |
| 4 | 语法错误 `.py` | 同上 |
| 5 | 声明的替代编码（PEP 263） | 同上 |
| 6 | 符号链接 | `test_robustness.py::test_symlink_is_skipped_with_reason` |
| 7 | 空仓库（无提交） | `test_robustness.py::test_empty_repository_has_reason_code` |
| 8 | 非 Git 目录 | `test_robustness.py::test_non_git_directory_degrades_without_crashing` |
| 9 | 浅克隆 | `test_robustness.py::test_shallow_clone_degradation_reaches_analysis_result` |
| 10 | 只读 / 无权限文件 | `test_robustness.py::test_unreadable_file_gets_reason_code` |
| 11 | 超深嵌套目录 | `test_robustness.py::test_deep_directory_does_not_crash` |
| 12 | 损坏的 Git 对象 | `test_robustness.py::test_git_object_failure_becomes_stage_diagnostic` |

### 选项

| 选项 | 含义 | 影响 |
|------|------|------|
| **A（建议）** | 确认这 12 类为最终分母 | 报告可直接写「12/12 通过」；无需额外工作 |
| B | 扩充 1–2 类（候选：CRLF/LF 混用、Git submodule、超长路径、只读目录） | 每类约 1–2 小时实现 + 验收；**但报告里"12 类"这个数字要改，之前写的都已固定** |
| C | 缩减（去掉不易复现的类） | 分母变小，但评审时会被问"为什么排除它" |

### 建议：**A**

理由：
1. 12 类已经覆盖三类失效来源——**输入内容**（1–5）、**仓库形态**（6–9）、**I/O 与对象损坏**（10–12）；
2. 继续扩充属于收益递减：真正罕见的场景（如 submodule、超长路径）在课程规模的项目里几乎不会遇到；
3. 改动分母会让已完成的三张对比表、`docs/nfr.md`、`sprint-2-nfr-acceptance.md` 全部需要同步，成本大于收益。

# 决策 2 · `--strict` 的致命范围

### 背景

`--strict` 目前的语义是：**只要有任何降级记录，就以退出码 3 终止**。降级有两类：

- **阶段级**：某阶段整体失败（如 git 采集抛错）→ `stage-failed`
- **文件级**：某个文件无法分析（`syntax-error`、`not-text`、`too-large`…）

问题：真实仓库里常有一两个二进制或生成文件。当前语义下，**这种仓库用 `--strict` 永远失败**。

### 现状证据

- 实现：`core/pipeline.py` 的 strict 分支判定 `stats.degradations or any(f.limitations for f in files)`
- 测试（两条边都已覆盖）：
  - `test_cli_smoke.py::test_strict_mode_exits_3_on_faulty_repo`
  - `test_cli_smoke.py::test_strict_mode_exits_0_on_clean_repo`
  - `test_pipeline_degradation.py`：降级文件在 `--limit` 之外时**仍然**退出 3

### 选项

| 选项 | 含义 | 影响 |
|------|------|------|
| **A（建议）** | 保持现状：任何降级都致命 | 语义最简单、最可预测；`--strict` 是 opt-in，默认模式已是 best-effort |
| B | 只有**阶段级失败**致命，文件级降级仅告警 | 更实用（含噪声文件的仓库也能用），但"哪个文件级降级算无害"变成新的主观判断 |
| C | 可配置：`--strict=all` / `--strict=stage` | 最灵活，但增加配置面与测试矩阵，且课程规模下大概率用不到 |

### 建议：**A**

理由：
1. `--strict` 是**显式选择**——用户加了它就表示"我要一个干净结果"，此时宁可严格；
2. 默认模式（`degrade`）已经提供 best-effort，想要宽松的人本来就不用 `--strict`；
3. 选 B 需要引入"容忍清单"，而这个清单本身又会变成一个需要维护的口径——正好是我们这个项目一直在批判的做法；
4. 如果实际使用中发现太吵，那时**有真实反馈**再升级为 C，比现在拍脑袋加配置更稳。

- 我们演示时会用真实仓库跑 `--strict` 吗？如果会，那个仓库里有没有二进制/生成文件？

# 决策 3 · 跨平台等价的边界

### 背景

NFR-3.3 要求「跨平台一致」。但**"一致"的严格程度**需要明确定义，否则验收时无法判定通过与否。

技术原因：同一个仓库在不同平台 checkout，git 可能因 `core.autocrlf` 产生不同的工作树内容，
进而影响 `churn`、`loc` 等指标。所以「两平台原始摘要完全相同」在一般仓库上**不成立**。

### 现状证据

当前实现（记为 D-3，见 `docs/nfr2-nfr3.md`）采用的是：

- 冻结夹具固定 `GIT_AUTHOR_DATE` / `GIT_COMMITTER_DATE`、`.gitattributes` 锁定 LF、注入固定时钟；
- 断言 **① 双跑自一致**（同一平台跑两次，指纹相同）+ **② checkout 路径无关**（同一内容在两个路径下指纹相同）；
- CI 在 **ubuntu + windows × Python 3.10–3.12** 上跑同一套测试。

测试位置：`tests/test_frozen_fingerprints.py`。

### 选项

| 选项 | 含义 | 影响 |
|------|------|------|
| **A（建议）** | 接受 D-3：自一致 + 路径无关，即为跨平台契约 | 现状即可验收；需在报告里说明"为什么不是原始摘要相同" |
| B | 要求两平台**原始摘要完全相同** | 需要做工作树规范化（`core.autocrlf=false`、`.gitattributes` 全覆盖、禁止 CRLF），对**外部仓库**仍无法保证；工作量大且边界仍然漏 |
| C | 只在 Linux 做指纹，Windows 只跑功能测试 | 最省事，但等于承认"跨平台一致"没被验证——与 NFR-3.3 的表述冲突 |

### 建议：**A**

理由：
1. 工作树规范化的差异是**git 的行为，不是我们工具的行为**——要求原始摘要跨平台相同，等于把 git 的约束算到我们头上；
2. 「双跑自一致 + 路径无关」恰好覆盖了**我们工具自身**的非确定性来源（时钟、路径、排序、浮点），这是可归因的；
3. 这个选择已经写进决策日志（D-3），且 CI 双平台在跑；改成 B 会把已完成的夹具重做一遍。
