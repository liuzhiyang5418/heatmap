# Evaluation toolkit

四个脚本，对应 `docs/evaluation-contract.md` 的执行阶段。契约本身是冻结的，这里只提供
**执行手段**——不改变任务、指标或阈值。

> **v1.1（2026-11-23）变更**：契约 v1.1 放弃外部参与者研究（Q3），Q2 改由**历史回放**
> 回答。因此 `historical_replay.py` 是当前唯一会真正跑起来的方法；下面三个参与者脚本
> 保留备用，**未执行过任何会话**，其产出不得作为结果报告。

| 脚本 | 作用 | 状态 |
|---|---|---|
| `historical_replay.py` | 在 `t0` 给仓库打分，再看后续窗口真实改动了什么 | ✅ **当前主方法（Q2）** |
| `build_answer_key.py` | 从**固定快照**算出 T1/T2/T4 的答案键，并给出 T3 的候选与指标明细 | ⏸️ Q3 已放弃，备用 |
| `run_pilot.py` | 逐题引导参与者、计时、记录答卷（匿名） | ⏸️ 未执行 |
| `score_responses.py` | 按契约 §5 给答卷打分并汇总 | ⏸️ 未执行 |

## 1. 历史回放 — 回答 Q2（主方法）

做法：把仓库 checkout 到 `t0`，用当时的快照正常跑一遍分析器得到排名；然后统计 `t0..t1`
之间**实际**每个文件的改动量；最后看「工具排在前 K 的文件」与「真的被改的文件」重合多少。

```bash
python examples/evaluation/historical_replay.py \
    --repo . --from daf9500 --to HEAD \
    --mode roi --top-k 10 --out replay.json
```

输出示例（本仓库实测，完整解读见 `docs/evaluation-replay-result.md`）：

```
窗口: 48 个提交 / 15.9 天
t0 评分文件: 65    窗口内改动: 60    可比对: 30    被删除: 0
Top-10 命中: 9/10  (Precision@10 = 90.0%)
随机基线:            4.6/10  (46.2%)
Lift:                1.95x
Recall@10:           50.0%
Spearman rho:        0.2262
```

### 读这些数字时必须知道的三件事

1. **主指标是 Lift，不是 Precision。** 窗口内 65 个文件里有 30 个被改动，瞎选也有 46 %
   命中率；Precision 90 % 只说明「比瞎选好」，Lift 1.95× 才是「好多少」。
2. **窗口必须 ≥ 一个迭代周期，且窗口内干的必须是产品代码。** 短窗口实测 Lift 会掉到
   1 以下（0.94×）：历史热点信号以周为单位更新，1.9 天的窗口测的是「这周任务碰巧落在哪」，
   不是代码健康度。窗口只改文档/脚本时，回放不回答任何问题。
3. **脚本会自己拦。** 可比对文件少于 `2×top_k` 时打印 `!! 样本量不足`，并把这些警告写进
   JSON 的 `warnings`。看到警告就不许把数字写成结论。

### 为什么不再招人

回放不需要参与者、没有标注偏差、任何人拿仓库都能复现，且直接对照现实改动而非主观评价。
代价是它衡量的是**预测重合度**，不是**对开发者有没有用**——后者是 Q3，已被放弃，
在报告中必须写成**未回答**，不能拿回放结果冒充。

## 2. 参与者研究 — 回答 Q3（**已放弃，未执行**）

> 以下流程从未运行过。保留是因为将来若恢复 Q3，这里是现成的执行手段。**任何一条产出
> 都不得写进本项目的评估结果**。

### 2.1 前置：把快照钉死

答案键必须绑定**具体提交**，否则参与者看到的数据与你算答案用的数据不是同一份：

```bash
git -C <repo> rev-parse HEAD          # 记下这个 sha
```

`build_answer_key.py` 会把 `repo_head` 写进答案键。若该字段为空（非 Git 目录），
说明快照不可复现，不要用它做正式评估。

### 2.2 生成答案键

```bash
python examples/evaluation/build_answer_key.py \
    --repo <快照路径> --data X --mode roi \
    --out answer_key_X.json
```

产出内容（节选）：

```jsonc
{
  "repo_head": "ac54bbd...",          // 快照绑定
  "T1": {"rule": "score desc, path asc", "answer": [ {...}, {...}, {...} ]},
  "T2": {"rule": "high/total desc, directory asc", "answer": {...}},
  "T3": {"candidates": [ ... ]},      // 解释题候选，答案需人工撰写
  "T4": {"rule": "status == missing", "answer": [ ... ]}
}
```

**T3 是唯一需要人工的一题**：从 `--show-t3-candidates` 里挑一个文件，写出「引用哪两项指标、
为什么它属于候选而非确诊」的标准答案，记进答案键的 `T3.expected` 字段后再分发。

```bash
python examples/evaluation/build_answer_key.py --repo . --data X --show-t3-candidates
```

> **T2 的「高分」怎么定义**：答案键用**该数据集分数的第 75 百分位**作阈值（top 25%），
> 而不是 `severity ≥ high`。原因是后者依赖绝对阈值（75/50），小仓库上可能一个文件都够不到
> ——实测本仓库 `roi` 模式最高分仅 24.99，T2 会变成无解。分位数定义随数据集自适应，
> 实际阈值会写进答案键的 `high_score_threshold`，口径因此仍然冻结。

### 2.3 跑试点

契约 §6 要求**先导 2 人**检查说明、难度与时限。流程：

```bash
# 1) 先生成参与者要看的报表（数据 X，与答案键同一快照、同一模式）
python -m githotmap analyze --repo-path <快照路径> --mode roi --output-file report_X.html

# 2) 打开报表，然后跑引导脚本
python examples/evaluation/run_pilot.py \
    --participant P01 --data X --report report_X.html --out-dir responses
```

每题默认 180 秒时限；超时**不中断**，只在答卷里标 `over_limit`，由评分脚本单独报告
（契约 §5 要求失败与超时单列，不能只统计成功者）。

### 2.4 组内成员参与 pilot 的规矩

- **pilot 可以用组内成员**——契约 §6 本来就要求先导 2 人。
- **正式数据不建议**：组内成员知道实现与预期结果，存在利益冲突。
- 若最终只能用组内样本，**必须在报告中披露**「便利样本、参与者来自团队内部」，
  并说明这不构成独立用户验证。
- 同一人不要同时参与 X 与 Y 两个数据集，否则学习效应会污染设计。

### 2.5 打分

```bash
python examples/evaluation/score_responses.py \
    --key answer_key_X.json --responses responses/ --out scores_X.json
```

输出示例：

```
参与者  数据     T1   T2   T3*  T4   总计   耗时(s)  超时
P01     X         3    2    2    1    8/9     412.3  -
P02     X         2    1    1    1    5/9     538.0  T2,T3
* T3 为自动粗筛结果，契约要求人工复核后再入表。
```

**T3 必须人工复核**：脚本只检查「是否出现两项指标关键词」和「是否有候选≠确诊的表述」，
无法判断推理是否正确。

## 3. 报告时不要做的事

契约 §7 已经冻结，这里再强调四条最容易犯的：

| 不要 | 为什么 |
|---|---|
| 只报成功完成的会话 | 超时与放弃必须单列，否则完成率被高估 |
| 看到地图表现差就删掉那道题 | 事后删题等于改目标 |
| 把 T1 得分当成「评分准确」的证据 | 它只证明参与者读对了排序，不证明排序本身有意义 |
| 拿回放结果去回答 Q3 | 回放测的是「文件会不会被改」，不是「人读地图是否更快」 |

另有一条 v1.1 新增的：**只报好看的窗口**。契约 §11.4 冻结了窗口选择规则，
本仓库那个 Lift 0.94× 的短窗口必须一起报告——它恰恰界定出了方法的适用条件。

---

## 4. 数据最小化

- 答卷只含：匿名 ID、数据集标识、各题答案、耗时、是否超时。
- **不要**采集姓名、邮箱、IP、设备信息、浏览器指纹。
- 公开报告使用匿名 ID；原始答卷不入库（`responses/` 建议加进 `.gitignore`）。
- 历史回放不接触任何个人数据，只读 Git 历史。
